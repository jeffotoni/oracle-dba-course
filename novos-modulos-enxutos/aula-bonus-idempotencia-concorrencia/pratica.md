# Laboratório bônus - Idempotência e concorrência

Este laboratório usa a tabela `PAYMENTS` para demonstrar duplicidade, constraint `UNIQUE`, espera entre sessões e duas operações concorrentes em Go.

Os comandos SQL podem ser executados no Oracle SQL Developer, CloudBeaver, DBeaver ou equivalente. O programa Go será executado no terminal e usará o driver `github.com/sijms/go-ora/v2`.

## 2. Criar a tabela de pagamentos

Conecte como `APP_AULA1` na `FREEPDB1` e crie a tabela sem a proteção de idempotência:

```sql
CREATE TABLE payments (
    id              NUMBER GENERATED BY DEFAULT AS IDENTITY,
    idempotency_key VARCHAR2(100) NOT NULL,
    account_id      NUMBER NOT NULL,
    amount          NUMBER(12,2) NOT NULL,
    status          VARCHAR2(20) NOT NULL,
    created_at      TIMESTAMP DEFAULT SYSTIMESTAMP,
    CONSTRAINT pk_payments PRIMARY KEY (id)
);
```

Neste primeiro momento existe uma chave primária para o registro físico, mas ainda não existe uma regra impedindo a repetição da operação lógica.

Confira a estrutura:

```sql
SELECT constraint_name,
       constraint_type
FROM user_constraints
WHERE table_name = 'PAYMENTS'
ORDER BY constraint_name;
```

## 3. Primeiro teste: duplicidade sem proteção

Execute a primeira operação:

```sql
INSERT INTO payments (
    idempotency_key,
    account_id,
    amount,
    status
)
VALUES (
    'PAY-ABC-123',
    10,
    150.00,
    'PROCESSED'
);

COMMIT;
```

Execute exatamente a mesma operação novamente:

```sql
INSERT INTO payments (
    idempotency_key,
    account_id,
    amount,
    status
)
VALUES (
    'PAY-ABC-123',
    10,
    150.00,
    'PROCESSED'
);

COMMIT;
```

Consulte os registros:

```sql
SELECT id,
       idempotency_key,
       account_id,
       amount,
       status,
       created_at
FROM payments
ORDER BY id;
```

O resultado terá dois registros com a mesma `idempotency_key`:

```text
PAY-ABC-123 -> R$ 150,00
PAY-ABC-123 -> R$ 150,00
```

O Oracle aceitou os dois comandos porque a tabela ainda não tinha uma regra de unicidade para a chave lógica.

## 4. Adicionar a proteção `UNIQUE`

Limpe os dados do teste:

```sql
TRUNCATE TABLE payments;
```

Adicione a regra de unicidade:

```sql
ALTER TABLE payments
ADD CONSTRAINT uk_payments_idempotency
UNIQUE (idempotency_key);
```

Agora a regra passou a ser garantida pelo Oracle:

```text
uma idempotency_key -> no máximo um registro
```

Confirme a constraint:

```sql
SELECT constraint_name,
       constraint_type
FROM user_constraints
WHERE table_name = 'PAYMENTS'
ORDER BY constraint_name;
```

### 5.1. Unicidade dentro de um contexto

Em alguns sistemas, a mesma chave pode existir para contas diferentes:

```text
conta 10 + PAY-001
conta 20 + PAY-001
```

Nesse caso, a regra pode ser composta por `account_id` e `idempotency_key`:

```sql
TRUNCATE TABLE payments;

ALTER TABLE payments
DROP CONSTRAINT uk_payments_idempotency;

ALTER TABLE payments
ADD CONSTRAINT uk_payments_account_idem
UNIQUE (account_id, idempotency_key);
```

Agora a unicidade vale para o conjunto:

```text
(account_id, idempotency_key)
```

Para a sequência principal da aula, a regra simples com `idempotency_key` já é suficiente. A constraint composta representa uma evolução comum de modelagem.

## 6. Por que não usar apenas `SELECT COUNT(*)`?

Uma tentativa comum seria:

```sql
SELECT COUNT(*)
FROM payments
WHERE idempotency_key = 'PAY-ABC-123';
```

Se o resultado for `0`, a aplicação executaria o `INSERT`. O problema é que duas sessões podem consultar antes de qualquer uma confirmar a inclusão:

```text
SESSÃO 1                         SESSÃO 2

SELECT COUNT(*)                  SELECT COUNT(*)
        -> 0                             -> 0

INSERT                           INSERT
```

As duas sessões observaram a mesma ausência. O `SELECT` não transforma a ausência em uma reserva exclusiva.

A proteção correta precisa estar no banco:

```sql
UNIQUE (idempotency_key)
```

## 7. Teste manual com duas sessões Oracle

Limpe o registro de teste e prepare uma nova chave:

```sql
DELETE FROM payments
```

Abra duas conexões como `APP_AULA1`, ambas na `FREEPDB1`.

Execute o `INSERT`, mas não faça `COMMIT` ainda:

```sql

    idempotency_key,

    amount,
    status
)

    'PAY-CONCURRENT-001',
```


### Voltar para a sessão 1

Confirme a primeira transação:



```sql

       account_id,
       amount,

WHERE idempotency_key = 'PAY-CONCURRENT-001';
```

O resultado deve conter somente um registro.

## 8. Concorrência com Go

Agora vamos disparar duas operações quase simultâneas a partir de duas goroutines.

### 8.1. Preparar um diretório temporário

No terminal do host:

```bash
mkdir -p /tmp/oracle-idempotencia
cd /tmp/oracle-idempotencia
go mod init oracle-idempotencia
go get github.com/sijms/go-ora/v2
```

Crie o arquivo `main.go` nesse diretório com o conteúdo abaixo:

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"sync"

	_ "github.com/sijms/go-ora/v2"
)

func main() {
	db, err := sql.Open(
		"oracle",
		"oracle://app_aula1:AppAula1_123@localhost:1522/FREEPDB1",
	)
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	db.SetMaxOpenConns(2)
	db.SetMaxIdleConns(2)

	if err := db.PingContext(context.Background()); err != nil {
		log.Fatal(err)
	}

	const query = `
		INSERT INTO payments (
			idempotency_key,
			account_id,
			amount,
			status
		)
		VALUES (:1, :2, :3, :4)
	`

	start := make(chan struct{})
	var waitGroup sync.WaitGroup

	for worker := 1; worker <= 2; worker++ {
		waitGroup.Add(1)

		go func(worker int) {
			defer waitGroup.Done()
			<-start

			_, err := db.ExecContext(
				context.Background(),
				query,
				"PAY-GO-CONCURRENT-001",
				10,
				150.00,
				"PROCESSED",
			)

			if err != nil {
				fmt.Printf("worker %d -> ERRO: %v\n", worker, err)
				return
			}

			fmt.Printf("worker %d -> INSERT OK\n", worker)
		}(worker)
	}

	close(start)
	waitGroup.Wait()
}
```

### 8.2. Executar o programa

```bash
go run .
```

A ordem pode variar:

```text
worker 1 -> INSERT OK
worker 2 -> ERRO: ORA-00001 ...
```

ou:

```text
worker 2 -> INSERT OK
worker 1 -> ERRO: ORA-00001 ...
```

O importante é que somente uma operação seja aceita.

### 8.3. Validar no Oracle

## 9. Concorrência e lock de linha

Agora o problema é diferente. Não estamos repetindo a mesma operação. Duas operações diferentes tentarão alterar o mesmo saldo:

```text
saldo inicial = R$ 100,00

transação A -> débito de R$ 80,00
transação B -> débito de R$ 80,00
```

Sem coordenação, as duas transações poderiam ler o mesmo saldo de `R$ 100,00` e concluir que existe dinheiro suficiente.

### 9.1. Criar a tabela de contas

Conecte como `APP_AULA1` e execute:

```sql
CREATE TABLE accounts (
    id         NUMBER PRIMARY KEY,
    holder     VARCHAR2(100) NOT NULL,
    balance    NUMBER(12,2) NOT NULL,
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT chk_accounts_balance CHECK (balance >= 0)
);
```

O `CHECK` impede que o banco aceite saldo negativo, mas não coordena duas transações. Para isso, usaremos `FOR UPDATE`.

Insira o saldo inicial:

```sql
INSERT INTO accounts (id, holder, balance)
VALUES (1, 'Cliente 01', 100.00);

COMMIT;
```

### 9.2. Consulta normal

Uma consulta comum apenas lê o registro:

```sql
SELECT id,
       holder,
       balance
FROM accounts
WHERE id = 1;
```

Ela não reserva a linha para uma alteração posterior.

### 9.3. Consultar com `FOR UPDATE`

Dentro de uma transação, use:

```sql
SELECT id,
       holder,
       balance
FROM accounts
WHERE id = 1
FOR UPDATE;
```

O fluxo é:

```text
SELECT ... FOR UPDATE
        -> linha bloqueada
            -> valida saldo
                -> UPDATE
                    -> COMMIT ou ROLLBACK
                        -> lock liberado
```

O lock permanece até o fim da transação. Não execute `COMMIT` ou `ROLLBACK` antes de terminar a decisão e a alteração.

## 10. Executar um débito protegido

Consulte e bloqueie a linha:

```sql
SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;
```

Com saldo de `100`, valide a regra:

```text
100 >= 80 -> débito permitido
```

Atualize o saldo e confirme na mesma transação:

```sql
UPDATE accounts
SET balance = balance - 80
WHERE id = 1;

COMMIT;
```

Valide:

```sql
SELECT id,
       holder,
       balance
FROM accounts
WHERE id = 1;
```

O saldo esperado é `20`.

## 11. Testar dois débitos em duas sessões

Primeiro restaure o estado inicial:

```sql
UPDATE accounts
SET balance = 100
WHERE id = 1;

COMMIT;
```

Abra duas conexões como `APP_AULA1` na `FREEPDB1`.

### Sessão 1

Execute e não confirme ainda:

```sql
SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;
```

O resultado será `100` e a linha ficará bloqueada.

### Sessão 2

Execute o mesmo comando:

```sql
SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;
```

A sessão 2 ficará aguardando a liberação do lock mantido pela sessão 1.

### Voltar para a sessão 1

Faça o primeiro débito e confirme:

```sql
UPDATE accounts
SET balance = balance - 80
WHERE id = 1;

COMMIT;
```

### Retorno da sessão 2

Depois que o lock for liberado, a sessão 2 continuará com o saldo atualizado:

```text
saldo lido pela sessão 2 = 20
```

A regra deve ser avaliada novamente:

```text
20 >= 80 -> não
```

Portanto, o segundo débito não deve ser executado. Faça:

```sql
ROLLBACK;
```

Valide o saldo final:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

Resultado esperado:

```text
20
```

### 11.1. Por que validar depois do lock?

Evite esta ordem:

```text
SELECT balance
    -> valida saldo
        -> SELECT FOR UPDATE
            -> UPDATE
```

Entre a leitura e o lock, outra sessão pode alterar o saldo. A ordem segura é:

```text
SELECT ... FOR UPDATE
    -> lê o estado protegido
        -> valida saldo
            -> UPDATE
                -> COMMIT
```

Primeiro bloqueie o registro que será alterado. Depois tome a decisão usando o estado protegido.

## 12. Reforçar a regra no `UPDATE`

Outra abordagem é colocar a condição crítica junto da alteração:

```sql
UPDATE accounts
SET balance = balance - 80
WHERE id = 1
  AND balance >= 80;
```

Interprete o resultado da operação:

```text
1 linha alterada  -> débito realizado
0 linhas alteradas -> saldo insuficiente ou conta inexistente
```

Essa abordagem é útil para manter a condição junto do `UPDATE`. O `SELECT ... FOR UPDATE` continua sendo didático para visualizar o lock e a espera entre sessões.

## 12.1. Testar a proteção `CHECK`

A tabela foi criada com:

```sql
CONSTRAINT chk_accounts_balance CHECK (balance >= 0)
```

Uma tentativa de persistir saldo negativo deve ser rejeitada:

```sql
UPDATE accounts
SET balance = -60
WHERE id = 1;
```

O Oracle deve retornar erro semelhante a:

```text
ORA-02290: check constraint violated
```

O `CHECK` não decide se uma operação financeira é permitida. Ele impede que um estado inválido seja gravado mesmo se alguma camada anterior falhar.

## 13. Concorrência com Go: débito protegido

Este é um segundo exemplo Go, separado do exemplo de idempotência. Agora duas goroutines tentarão debitar `R$ 80,00` da mesma conta de `R$ 100,00`.

### 13.1. Preparar o estado

Antes de executar o programa, deixe a conta com `R$ 100,00`:

```sql
UPDATE accounts
SET balance = 100
WHERE id = 1;

COMMIT;
```

No terminal do host, use o diretório temporário já criado para o exemplo anterior:

```bash
cd /tmp/oracle-idempotencia
```

Substitua o conteúdo de `main.go` pelo programa abaixo:

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"sync"

	_ "github.com/sijms/go-ora/v2"
)

func debit(ctx context.Context, db *sql.DB, worker int, accountID int64, amount float64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}

	var balance float64
	err = tx.QueryRowContext(ctx, `
		SELECT balance
		FROM accounts
		WHERE id = :1
		FOR UPDATE
	`, accountID).Scan(&balance)
	if err != nil {
		_ = tx.Rollback()
		return err
	}

	if balance < amount {
		_ = tx.Rollback()
		return fmt.Errorf("worker %d: saldo insuficiente: %.2f", worker, balance)
	}

	_, err = tx.ExecContext(ctx, `
		UPDATE accounts
		SET balance = balance - :1
		WHERE id = :2
	`, amount, accountID)
	if err != nil {
		_ = tx.Rollback()
		return err
	}

	return tx.Commit()
}

func main() {
	db, err := sql.Open(
		"oracle",
		"oracle://app_aula1:AppAula1_123@localhost:1522/FREEPDB1",
	)
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	db.SetMaxOpenConns(2)
	db.SetMaxIdleConns(2)

	if err := db.PingContext(context.Background()); err != nil {
		log.Fatal(err)
	}

	start := make(chan struct{})
	var waitGroup sync.WaitGroup

	for worker := 1; worker <= 2; worker++ {
		waitGroup.Add(1)

		go func(worker int) {
			defer waitGroup.Done()
			<-start

			err := debit(context.Background(), db, worker, 1, 80.00)
			if err != nil {
				fmt.Println(err)
				return
			}

			fmt.Printf("worker %d: débito realizado\n", worker)
		}(worker)
	}

	close(start)
	waitGroup.Wait()
}
```

### 13.2. Executar o programa

```bash
go run .
```

A ordem pode variar, mas o resultado esperado é semelhante a:

```text
worker 1: débito realizado
worker 2: saldo insuficiente: 20.00
```

Ou o inverso:

```text
worker 2: débito realizado
worker 1: saldo insuficiente: 20.00
```

O `SELECT ... FOR UPDATE` garante que apenas uma transação leia e altere a conta por vez. A segunda transação espera, lê o saldo atualizado e rejeita o débito.

## 14. O que a aplicação real faria?

Nesta primeira demonstração, a segunda tentativa recebe um erro de constraint. Uma API real pode tratar esse erro e buscar o resultado já gravado:

```text
primeira chamada
    -> processa
    -> grava
    -> retorna sucesso

repetição da mesma chave
    -> identifica a chave existente
    -> retorna o resultado anterior
```

Para isso, uma tabela real pode armazenar também informações como:

```text
status da operação
resposta original
data de processamento
código HTTP
identificador do recurso criado
```

Esse é um próximo passo. Nesta aula, a garantia principal da repetição é a unicidade da chave no Oracle, enquanto a garantia do saldo depende da transação, do lock de linha e do `CHECK`.

## 16. Resultado esperado

Ao finalizar, a sequência deve estar clara:

```text
mesma solicitação
    -> mesma chave
        -> constraint UNIQUE
            -> uma operação efetiva

dois débitos concorrentes
    -> SELECT ... FOR UPDATE
        -> saldo protegido
            -> um débito realizado
                -> saldo final consistente
```

A aplicação pode receber duas tentativas ou dois débitos simultâneos, mas o banco continua protegendo a integridade da operação.
